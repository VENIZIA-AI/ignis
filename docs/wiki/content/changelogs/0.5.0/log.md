IGNIS 0.5.0 is a typing and network release. Binding keys carry the type of their value, the fetchers and the url guard are one family that validates, retries and guards each call, and the origins you trust are named in one format for the url guard and for JWKS. It also adds mail template sections, Typesense import options and BullMQ job metadata. Several changes are breaking, and each entry says what to change.

## Breaking
- **A route handler's context is typed from its route** `typed-route-context` (`@venizia/ignis-kernel`, `@venizia/ignis`): the handlers of `defineRoute`, `defineJSXRoute` and `bindRoute().to` take their context's types from `configs`, and a decorated method names its route with the new `TContextOf<typeof CONFIG, Env?>`. `context.req.valid(target)` without a type argument now answers the schema's output type, or `unknown` for a part the config does not declare; a line that took its type from the annotation or the return around the call must change. `valid<T>(target)` keeps working. `TRouteContext<Env, Body>` is `TRouteContext<Env>`, `TRouteHandler<Response, Env>` is `TRouteHandler<Env>`, the `ResponseType` type argument of `defineRoute`, `defineJSXRoute`, `bindRoute().to` and `toHonoHandler` is gone, and `IValidRequestProps` and `TResponseBodyOf` are no longer exported. `context.json()` and `TContext` are unchanged. In a package that emits `.d.ts` files, an exported value whose inferred type holds `context.req` or `context.req.valid` now fails with TS2883, migrated or not: write its type, `TRouteContext['req']` or `TContextOf<typeof CONFIG>['req']`. Run `bun node_modules/.bin/devz codemod typed-route-context [paths...] --write`.
- **The house lint rules check typed route handlers** `typed-route-context-rule` (`@venizia/dev-configs`): `houseConfigs` and `reactHouseConfigs` now report, as errors, in tests too, `@venizia/typed-route-context`: an object declared as `IAuthRouteConfig` (or in a `Record` of it) instead of `satisfies`, `valid<T>()` on a context typed from its route, a `TContextOf` naming another route than the method's decorator, and a handler passing its context to a method of its class typed for another route. It reads syntax only.
- **IAuthRouteConfig is IGNIS's own type** `light-route-config` (`@venizia/ignis-kernel`, `@venizia/ignis`): it no longer extends Hono's `RouteConfig`, which makes type checking route configs cheaper (about 10 to 16% fewer type instantiations on a test application). It does not take `requestBody` (write `request.body`) or `method: 'query'`, and a member it does not name is an excess-property error. `schema` of a content entry is a zod schema or a raw OpenAPI object. `configs` of `IDefineRouteOptions` is typed as the config you gave: `getRoutingPath()` is no longer on its type (at run time nothing changed). Code that passes an `IAuthRouteConfig` to a Hono API converts it itself. A `params` or `query` schema that is not an object is no longer refused by the type. A `request` part read off a value typed `IAuthRouteConfig` is no longer a zod type: check it with `instanceof` before calling zod on it, or declare the route with `satisfies IAuthRouteConfig`.
- **A CRUD create route declares 201** `crud-create-declares-201` (`@venizia/ignis-kernel`, `@venizia/ignis`): the generated create route has always answered 201 and now declares it instead of 200, so the OpenAPI document and a client generated from it change.
- **HttpDataSource hooks are `resolvers.headers` and `resolvers.authToken`** `http-datasource-resolvers` (`@venizia/ignis-connectors`, `@venizia/ignis`): the settings `headersResolver` and `authTokenResolver` are `resolvers: { headers, authToken }`, with no alias. What each does is unchanged, and so are `authToken` and `onUnauthorized`. An old name is refused when the datasource is built, also in an object that is spread or loosely typed and so compiles, such as the result of ARDOR's `getDataSourceAuth()`. No codemod.
- **The house lint rules report a hand-written HTTP method** `prefer-http-method-rule` (`@venizia/dev-configs`): in a project that depends on an IGNIS package, `houseConfigs` and `reactHouseConfigs` now report, as errors outside tests, `@venizia/prefer-http-method`: a method string such as `'get'` under `method`, `verb` or `httpMethod` in a route config or a request, or assigned to a variable of those names. Write `HTTP.Methods.GET`. `--fix` rewrites the exact lowercase value and adds the import; another spelling is reported only, since the constant is lowercase and a plain `fetch` sends `patch` as written. An object whose only member is `method`, outside a `fetch` call or `new Request`, is not reported.
- **HTTP is a module namespace, not a class** `http-namespace` (`@venizia/ignis-helpers`, `@venizia/ignis`): you still write `HTTP.Methods.GET`, and every group keeps its members in the same order, but `HTTP` is now a namespace of its groups, so a browser bundle keeps only the groups it reads (a bundle that reads `HTTP.Methods` alone is 9,375 → 4,959 bytes; `connectors/http` is 68,797 → 67,768). Only a static read, `HTTP.Methods`, drops the other groups: destructuring `HTTP`, reading `HTTP[key]` or passing `HTTP` itself keeps all six. `HTTP` is no longer a type, so it cannot annotate a value, and at run time `typeof HTTP` is `'object'`: `extends HTTP`, `new HTTP()` and `instanceof HTTP` no longer compile, `HTTP` cannot be assigned a member, and listing its keys gives the groups in alphabetical order. `typeof HTTP.Methods` and the other group types are unchanged.
- **ParseUtility.toBoolean reads boolean words and refuses the rest** `to-boolean-words` (`@venizia/ignis-helpers`, `@venizia/ignis-kernel`, `@venizia/ignis-connectors`, `@venizia/ignis`, `@venizia/dev-configs`): `true`, `1`, `yes`, `on`, `y`, `enabled` are `true` and `false`, `0`, `no`, `off`, `n`, `disabled` are `false`, trimmed and in any case, as `z.stringbool()` reads them. `"no"`, `"off"`, `"n"`, `"disabled"`, `"False"`, `" false "` and a blank string with spaces were `true` and are now `false`; another string, a number other than `1` and `0`, `NaN` and an object were `true` and now throw a 400. A boolean, `null`, `undefined` and `''` read as before; the new `name` option names the setting in the error. Where IGNIS reads a boolean: (1) `ALLOW_EMPTY_ENV_VALUE=no` or `off` now turns the empty-value check on, and a value that is no boolean word stops the boot; (2) the `x-request-count` header: `no`, `off`, `n` and `disabled` now answer the rows only, and any other value still answers `{ count, data }`; (3) `APP_ENV_AUTO_PROVISION_COLLECTION=yes`, `on`, `y` or `enabled` now provisions collections, and a value that is no boolean word stops the boot unless the `autoProvision` option is set; (4) `APP_ENV_LOGGER_COLOR=no`, `off`, `n` or `disabled` turned color on and now turns it off, and a value that is no boolean word now counts as unset (it turned color on); (5) `DEBUG=no`, `off`, `n`, `disabled`, `FALSE`, `False`, `' 0'`, `'false '` or spaces only turned `debug` on and now leaves it off, and every other value reads as before; (6) `APP_ENV_LOGGER_DO_REDACT` is unchanged: only `false` turns masking off, on purpose; (7) the `withUserInformation` and `recursive` query parameters are unchanged. The `@venizia/prefer-framework-api` lint rule now reports `AppEnvs.get(key) === 'true'` (and `'false'`) as an error.
- **The zod lint rule reports .strict() and .passthrough()** `zod-strict-and-passthrough` (`@venizia/dev-configs`): `@venizia/zod-schema-convention`, in `houseConfigs` and `reactHouseConfigs`, now reports as errors, in every file but tests, `z.object({ ... }).strict()` (`--fix` rewrites it to `z.strictObject({ ... })`) and `.passthrough()` on a schema the file itself builds from zod (write `z.looseObject`, or `.loose()`). The new `strictCall` and `noPassthrough` options switch them off. A new `noCoercePaths` option refuses `z.coerce` in the files you list, and is empty by default.
- **WebSocket authentication data and socket data are typed and checked** `websocket-payload-types` (`@venizia/ignis-helpers`, `@venizia/ignis`): the options of `WebSocketServerHelper` are scoped: `authenticateFn` is `authenticate: { fn }` and `handshakeFn` is `handshake: { fn }`, with no alias. Both receive the `data` of the `authenticate` message only when it is an object; any other value (a string, a number, a list, `null`, nothing) now fails authentication with close code `4003`. To give the data a type of your own, pass `authenticate.schema` (a zod schema): the server checks the data with it, refuses what it refuses, and the hooks receive what it answers, typed from the schema. `WebSocketComponent` takes it from the new `WebSocketBindingKeys.AUTH_SCHEMA`. Without a schema the type is `Record<string, unknown>`, and a hook typed with a data type of your own no longer compiles. `IWebSocketServerOptions` is now the type `TWebSocketServerOptions` (`bun node_modules/.bin/devz codemod class-renames [paths...] --write`), so `extends` it with an intersection. The callbacks of `IBunWebSocketHandler` take an `IWebSocket<IWebSocketData>`.
- **Schemas and types are renamed to the naming rules** `schema-and-type-names` (`@venizia/ignis-kernel`, `@venizia/ignis-helpers`, `@venizia/ignis-connectors`, `@venizia/ignis`): `trackableHeaders`, `countableHeaders` and `defaultRequestHeaders` become `TrackableHeadersSchema`, `CountableHeadersSchema` and `DefaultRequestHeadersSchema`, and `TErrorResponse` becomes `TErrorOutput` (the type follows `ErrorSchema`, which stays; `TError` is already the type `getError` takes); `vaultAuthSchema` becomes `VaultAuthSchema` and `ISecretsRegistration` becomes `TSecretsRegistration`; `IRelationalDataSourceOpening` becomes `TRelationalDataSourceOpening`. No alias is kept. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write`.
- **The house lint rules check zod schema names and type names** `zod-and-type-name-rules` (`@venizia/dev-configs`): `houseConfigs`, `reactHouseConfigs`, and for the type and interface names also `eslintConfigs`, `namingConventionConfigs` and `reactNamingConventionConfigs`, now report, as errors, a zod schema const that is not PascalCase ending in `Schema`, a type inferred from `XSchema` that is not `TX` or `XType` (`TXInput`, `TXOutput` where a schema has two), a type alias that neither starts with `T` nor ends with `Type`, and an interface that does not start with `I`. The zod rule (`@venizia/zod-schema-convention`) skips tests; the type and interface names are selectors of `naming-convention` and apply to every file, so an app's tests fail lint too. Strict objects and `z.any()` are checked only in the files you list in `strictPaths` and `noAnyPaths`.
- **The oxlint preset reports `function`, `console` and a `switch` without `default`** `oxlint-base-rules` (`@venizia/dev-configs`): `oxlintConfigs` and the presets built on it now run `func-style` (arrows and function expressions), `no-console` and `default-case` as errors. Test files are exempt. A file whose job is writing to the console turns `no-console` off for itself in the package's oxlint config. `oxlint --fix` rewrites none of the three: `devz codemod function-to-arrow` rewrites the function declarations, and the other two are edited by hand.
- **Middleware options and the filter schemas are no longer `any`** `middleware-options-unknown` (`@venizia/ignis-kernel`, `@venizia/ignis`, `@venizia/ignis-filter`): the `middlewares` option of `setupMiddlewares` is `Record<string | symbol, unknown>`, and the recursive `where` and include `scope` schemas of `QuerySchemaFactory` are typed as `TWhere` and `TFilter`. A subclass that reads a value out of `middlewares` narrows it before use.
- **The house lint rules are `@venizia/` rules** `lint-rule-namespace` (`@venizia/dev-configs`): every house rule is renamed from `venizia/<rule>` to `@venizia/<rule>`. An ESLint config that sets a `venizia/` rule to anything but `off` stops ESLint with `Could not find plugin "venizia"`, and a `venizia/` disable comment reports `Definition for rule ... was not found`. Replace `venizia/` with `@venizia/` in your ESLint configs and disable comments.
- **RetryHelper is RetryUtility** `retry-helper-is-utility` (`@venizia/ignis-helpers`, `@venizia/ignis`): `RetryHelper` only had static members, so it is renamed `RetryUtility` with the same members. It no longer extends `BaseHelper`, so `instanceof BaseHelper`, the inherited constructor and the instance logger are gone. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write` to rename the import and every use. No alias is kept.
- **SlugHelper is SlugUtility** `slug-helper-is-utility` (`@venizia/ignis-helpers`, `@venizia/ignis`): `SlugHelper` only had static members, so it is renamed `SlugUtility` with the same members. It no longer extends `BaseHelper`. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write` to rename the import and every use. No alias is kept.
- **CredentialHelper is CredentialUtility** `credential-helper-is-utility` (`@venizia/ignis-helpers`, `@venizia/ignis`): `CredentialHelper` only had static members, so it is renamed `CredentialUtility` with the same members. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write` to rename the import and every use. No alias is kept.
- **RejectionHelper is RejectionUtility** `rejection-helper-is-utility` (`@venizia/dev-configs`): `RejectionHelper` only had static members, so it is renamed `RejectionUtility` with the same members. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write` to rename the import and every use. No alias is kept.
- **SpawnHelper is SpawnUtility** `spawn-helper-is-utility` (`@venizia/dev-configs`): `SpawnHelper` only had static members, so it is renamed `SpawnUtility` with the same members. Run `bun node_modules/.bin/devz codemod class-renames [paths...] --write` to rename the import and every use. No alias is kept.
- **parseContentDisposition moves to HttpResponseReader** `parse-content-disposition-in-reader` (`@venizia/ignis-helpers`, `@venizia/ignis`): `RequestUtility.parseContentDisposition({ header })` is now `HttpResponseReader.parseContentDisposition({ header })` and returns the same answer. A browser client can read the header without importing `RequestUtility`, which needs `node:*`. `ContentDispositionTypes` is imported as before. Replace the call by hand. `devz codemod namespace-functions` only rewrites the older bare `parseContentDisposition` function to the new method.
- **HttpDataSource works with a Headers object** `http-datasource-headers-object` (`@venizia/ignis-connectors`, `@venizia/ignis`): the protected `configuredHeaders`, `resolveHeaders()` and the `requestHeaders` option of `buildHeaders()` are now a `Headers`, not arrays of `[name, value]` pairs. The connectors' own `THttpHeaders` is gone: use the `THttpHeaders` of `@venizia/ignis-helpers`, which is a `Headers`, pairs or a record. A number value is sent as text. A `null` value removes the header, but only within the same layer: a call's `null` does not remove a configured or resolved header. If a subclass overrides `buildHeaders` or `resolveHeaders`, update the types it reads and returns. `settings.headers`, `headersResolver` and a call's `headers` accept what they accepted before. There is no codemod.
- **HttpResponseReader moves to @venizia/ignis-helpers** `http-response-reader-in-helpers` (`@venizia/ignis-helpers`, `@venizia/ignis-kernel`, `@venizia/ignis-connectors`, `@venizia/ignis`): import `HttpResponseReader` from `@venizia/ignis-helpers` (or `/core`), no longer from `@venizia/ignis-kernel/repository` or `@venizia/ignis-connectors/http`. Its `isPlainObject` is now `RecordUtility.isPlainObject`, and `toText` is private. Change the import; the methods are the same. There is no codemod.
- **allowedHosts is replaced by hosts.trusted and hosts.strict** `url-safety-hosts` (`@venizia/ignis-helpers`): `IUrlSafetyPolicy.allowedHosts` is removed. List exact origins in `hosts.trusted`, and add `strict: true` if nothing else may pass. A policy that still carries `allowedHosts` throws a configuration error that names the replacement, because dropping it silently would turn "only these hosts" into "any public host". A trusted origin also passes when it resolves to a private address.
- **jwks.hosts.http is replaced by jwks.trusted** `jwks-trusted-origins` (`@venizia/ignis-kernel`, `@venizia/ignis`): list the hosts a JWKS may be fetched from over `http:` as exact origins (`http://identity-service`, `http://10.0.0.5:8080`) in `jwks.trusted`. It covers the JWKS verifier and the service-assertion callers. Each port is its own entry; an entry without a port used to mean every port. An app that still sets `jwks.hosts.http` refuses to boot on its http JWKS URL until you list the origin.
- **The inner JWT options have keys of their own** `jwt-inner-option-keys` (`@venizia/ignis-kernel`, `@venizia/ignis`): `AuthenticateBindingKeys.JWT_OPTIONS` now holds only what your app binds, the `TJWTTokenServiceOptions` with its `standard`. Before, the component re-bound the same key to the inner `IJWSTokenServiceOptions`, and `JWKS_OPTIONS` held the issuer's or the verifier's options depending on the mode. Now `JWS_OPTIONS`, `JWKS_ISSUER_OPTIONS` and `JWKS_VERIFIER_OPTIONS` each hold one type, and `JWKS_OPTIONS` is removed. Nothing changes if your app binds `JWT_OPTIONS` and registers `AuthenticateComponent`. If a service of yours injects `JWT_OPTIONS` or `JWKS_OPTIONS` to read the inner options, inject the new key.
- **A binding key is made by BindingKeys.build&lt;T&gt; and nothing else** `binding-keys-required-brand` (`@venizia/ignis-inversion`, `@venizia/ignis-kernel`, `@venizia/ignis`): `bind`, `get`, `gets`, `getBinding`, `isBound`, `unbind`, `Binding.bind` and `@inject({ key })` accept only a key made by `BindingKeys.build<T>({ namespace?, key })`. A raw string, a template literal, a symbol and the `{ namespace, key }` object form of `get` and `getBinding` no longer compile, and `build` needs its type argument (`build<unknown>` when a key has no common value type). Key strings do not change, so nothing stored or sent changes. Run `devz codemod binding-keys`: it rewrites each literal key, moves the type your call already claimed into `build<T>`, and lists each key it left as `build<unknown>` so you can name the real type. A key your app keeps in a constant, such as `static readonly MAILER = 'services.Mailer'` in a key class, is built where it is declared, in any file of the run: `static readonly MAILER = BindingKeys.build<Mailer>({ key: 'services.Mailer' })`. The places that use `Keys.MAILER` are not edited, because the constant is still a string and now carries `Mailer`. For `T` the codemod uses the one type your code already claims where the key is used (`container.get<Mailer>`, the type of the decorated parameter), only when every name in it means the same type in the file that declares the constant (it adds no import); otherwise it writes `unknown`, and it does so too when no site claims a type or the sites differ (listed as `type`: name it). It builds a const, a `readonly` property and a property of an object literal under `as const` that has a string value and no type annotation, a computed one included (`` `${namespace}.Name` ``, `Mailer.name`). It lists as manual, and leaves alone, a `let`, a property that is not `readonly`, an object literal without `as const`, a declaration with a type annotation, a parameter, a call that returns a key, a declaration outside the files you pass, and a key of a package you do not own. Run it once over the whole project (from the root, or with every package path as arguments): a constant declared in a file outside the run is listed as manual and not edited. The codemod uses the compiler options of the nearest `tsconfig.json` above the folder you run it in; the files you pass are its roots, not the tsconfig's `include`, and there is no flag to choose another tsconfig: a test file whose imports need its own package's tsconfig (path aliases, test types) can leave a receiver unresolved, and the site is listed "the receiver's type is not resolved" and left alone. Run the codemod again from that package's folder for those files, or change them by hand. A key written inline with no claimed type is `build<unknown>` too, so the `type` list can be long: name each from your typecheck. A key written as `SomeClass.name` is the built-in `name` of a class, not a constant of yours: the codemod builds it in place, `BindingKeys.build<SomeClass>({ key: SomeClass.name })`. A keys file that imports nothing from the framework is listed "pass --import-from" and is not built until you pass `--import-from @venizia/ignis`. Where your code needs the literal type of a built constant (`typeof Keys.MAILER` as a type, a literal union, a parameter typed `'services.Mailer'`) or assigns to it, the typecheck now names the site. `BindingKeys.build` throws on an empty key, so a computed constant that comes out `''` now throws when its class loads. Change a `Symbol` key to a string key by hand. `@inject({ target: Class })` stays the form for a class. A library key that is still a plain string (ARDOR's `CoreBindings` before its release with typed keys, which follows this one) needs the library's typed version; the codemod lists such a key as manual. Reflect-metadata keys (`MetadataRegistry.define`/`get`) are `TMetadataKey`, a plain string or symbol. `@provide({ key })`, the `key` of an event handler `{ type: BINDING_KEY, key }` and the `serviceKey` of the auth controller take a built key too.
- **UrlIngest.fetchGuarded, capStream and readCappedBody are removed** `fetch-guarded-removed` (`@venizia/ignis-helpers`, `@venizia/ignis`): the guard now lives in the fetchers. Give a `NativeFetcher` or `AxiosFetcher` `guardEngine: UrlGuard`, and pass `guard`, `maxBytes`, `signal`, `maxRedirects` and `retry` on the call. `BodyLimit.capStream` and `BodyLimit.readBytes` replace the two body helpers. `StaticAssetIngestUtility.fromUrl` already does this.
- **NodeFetcher is now NativeFetcher** `native-fetcher-rename` (`@venizia/ignis-helpers`, `@venizia/ignis`): `NodeFetcher`, `NodeFetchNetworkRequest`, `INodeFetch*` and `FetcherVariants.NODE_FETCH` (`'node-fetch'`) are now `NativeFetcher`, `NativeFetchNetworkRequest`, `INativeFetch*` and `FetcherVariants.NATIVE` (`'native'`). No alias is kept. Rename them by hand with the table in the migration steps; there is no codemod.
- **send&lt;T&gt; is removed; pass a schema** `fetch-send-type-argument-removed` (`@venizia/ignis-helpers`): every verb and `send` take a zod `schema` and answer `{ data, status, headers, response }`, with `data` typed by `z.infer`. Without a schema the call answers the raw `Response` (`AxiosResponse`), as before.
- **A status outside 2xx throws** `fetch-non-2xx-throws` (`@venizia/ignis-helpers`, `@venizia/ignis`): both fetchers throw a `UrlFetchError` (with status, url, headers and response) instead of handing a 404 or 500 back as data. Use `acceptStatus` to opt out. The Axios default `validateStatus: status < 500` is gone, so a 4xx now throws too.
- **Headers merge per header, and defaultConfigs no longer carries headers or signal** `fetch-headers-merge` (`@venizia/ignis-helpers`): a call's headers merge with `defaults.headers` (a `null` or `undefined` layer is skipped) one header at a time. The call wins, and `null` or `undefined` removes a default. If your code relied on a call's headers replacing every default (a multipart upload without the JSON content type), remove that default with `null`. `NativeFetcher` takes `defaults.headers` in place of `defaultConfigs.headers`, and `timeout` now applies per attempt.
- **UrlIngest is merged into UrlGuard** `url-ingest-merged-into-guard` (`@venizia/ignis-helpers`, `@venizia/ignis`): `assertPublicHost`, `assertReachableUrl` and `resolvePublicAddresses` are now static methods of `UrlGuard`, next to `createRoute`, which a fetcher takes as `guardEngine`. The name `UrlIngest` no longer exists and no alias is kept. Rename by hand with the table in the migration steps; there is no codemod.
- **Exports with no caller are removed** `remove-unused-network-exports` (`@venizia/ignis-helpers`, `@venizia/ignis-connectors`, `@venizia/ignis`): these exports are gone: `QueryStringNullishModes`, `QueryStringNestedModes` and their types (`IQueryStringOptions.nullish` and `.nested` are now the literals `'empty' | 'skip'` and `'drop' | 'json'`), `TFetchResult`, `TUrlScheme`, `BodyLimit.DEFAULT_MAX_BYTES` and `FetchErrors` (the error code `core.fetch.schema_mismatch` is unchanged). From `@venizia/ignis-connectors/http`, `THttpQuery`, `TAuthTokenResolver`, `THttpHeadersResolver`, `HttpResourceEntity` and `THttpRepositoryOptions` are gone too (`THttpFetch` stays, as an alias of `TNativeFetchSender`). `UrlPolicy.readHosts` is no longer public. Rename or inline by hand with the table in the migration steps; there is no codemod.
- **getRequestUrl refuses paths that can leave the base** `get-request-url-strict-join` (`@venizia/ignis-helpers`, `@venizia/ignis`): `BaseNetworkRequest.getRequestUrl` now joins the base and the paths through the new `UrlBuilder.join`, the check the connectors' HTTP data source already ran. A path answers a `400` that starts `[<client name>] A request path must stay under the base path` when it is a dot segment (`..`, `%2e%2e`, `.%2e`, with a trailing space, or ended by `?` or `#`), or carries a backslash, `%5c` or a control character. A base with a `?` or a `#`, a path-relative base (`api`) and a result that leaves the base's origin or path are refused too. A relative base (`/api`) now answers the absolute url, resolved against the page's origin, and a path with a space is percent-encoded (`a%20b`).
- **A missing template value renders empty, and an object in a text slot throws** `mail-template-missing-empty` (`@venizia/ignis`): `TemplateEngineService` used to send a <code v-pre>{{key}}</code> the data did not have as literal text in the mail. It now renders nothing (`missing: 'empty'`, the default). Pass `missing: 'keep'` for the old output or `'throw'` to refuse. A value that is an object, a list, a date or a function in a <code v-pre>{{key}}</code> slot used to print `[object Object]` (or the function's source); it now throws `core.mail.template_invalid`. Resolve a locale object and format dates before rendering. - **Get an artifact by its class** `container-get-by-target` (`@venizia/ignis-inversion`, `@venizia/ignis`): `container.get({ target: UserService })` (and `application.get`) resolves a registered class typed as that class, with no key to rebuild and no cast. A type has no start or stop hook; drain its bindings by tag in a component when boot work is needed. Nothing changes for the seven built-in types.
- **HttpRepository.execute calls a route beside the CRUD routes, typed** `http-repository-execute` (`@venizia/ignis-connectors`, `@venizia/ignis-helpers`): a subclass calls `this.execute({ paths, method, body, schema, options })` for `POST auth/sign-up` and the like. Without a `schema` it returns `void`. `method` is POST unless given; `options` carry `headers` and `signal`; a non-2xx throws as every repository call does. `HttpDataSource.write` now also answers the `status` of the route, and `FetchSchemaError.fromZod({ status, url, error })` builds the error the fetchers already threw for a refused body.

An absolute call url is sent as it is, an empty one is the base itself, and a query or fragment passes as written (only the path part is checked). A url that starts with `//` is a path under the base, never another host. An `AxiosFetcher` built directly reads `defaultConfigs.baseURL` when it has no `baseUrl`; when both are set, `baseUrl` wins. - **A FormData, URLSearchParams or Blob body keeps no JSON content type** `fetcher-form-body-content-type` (`@venizia/ignis-helpers`, `@venizia/ignis`): `AxiosNetworkRequest` and `NativeFetchNetworkRequest` default to a JSON content type, so a `FormData` sent through them was written as JSON text (axios) or labelled JSON without a multipart boundary (fetch): a silent wrong upload, as in 0.4.8. The default is now dropped for a `FormData`, `URLSearchParams` or `Blob` body, so the runtime writes the boundary or the right type. A content type the call names stays. (axios still writes `application/octet-stream` for a `Blob`.)
- **A Content-Disposition with an empty or ISO-8859-1 filename** `content-disposition-empty-latin1` (`@venizia/ignis-helpers`): `HttpResponseReader.parseContentDisposition` and `readFile` answer `undefined` for an empty name (`filename=""`, `filename=`) and an empty `filename*` (it reads as absent, so the plain `filename` is the answer), and decode `filename*=ISO-8859-1''caf%E9.txt` as `café.txt`. Any other charset in `filename*` falls through to the plain `filename`. A quoted `filename="a\"b.pdf"` now reads `a"b.pdf`: `\"` and `\\` are unescaped as RFC 6266 writes them, where the name used to end at the backslash.
- **A bare % in a request path is escaped** `url-path-bare-percent` (`@venizia/ignis-helpers`, `@venizia/ignis`): `getRequestUrl`, `getRequestPath` and the fetchers' `baseUrl` join wrote a `%` that is not an escape (`100%`) as it was, which corrupts the url. It becomes `%25` in the path part (before the first `?` or `#`); a valid escape (`%20`, `%3F`) is left alone. A `?` or `#` in a path still starts the query or the fragment, as documented: write `%3F` or `%23` for the characters themselves.
- **A COMMIT the server turned into a ROLLBACK is reported** `commit-rolled-back` (`@venizia/ignis-connectors`): when a statement inside a transaction failed and your code carried on (a caught `23505`, say), Postgres aborts the transaction and answers `COMMIT` with `ROLLBACK`; `transaction.commit()` resolved as if the writes were saved. It now throws a `500` with the code `core.database.commit_rolled_back`, on postgres-js, node-postgres and PGlite. The transaction is over, so a following `rollback()` stays a no-op. The migration runner's `COMMIT` is checked the same way. It is a `500` and not a `409`: a retry would lose the writes again, and the cause is a failed statement in your own handler. Do not catch a failed statement inside the transaction: use `INSERT ... ON CONFLICT DO NOTHING`, decide by reading first under a lock, or map the error outside `runInTransaction`.
- **A queue's defaultJobOptions keep the clean-up defaults** `bullmq-default-job-options-merge` (`@venizia/ignis-helpers`): `queueOptions: { defaultJobOptions: { attempts: 3, backoff } }` replaced `removeOnComplete: true, removeOnFail: true` instead of adding to them, so finished jobs piled up in Redis. Your keys now merge over the two defaults, and a key you name still wins. A queue that set `{ attempts: 3 }` used to keep failed jobs (BullMQ's default) and now removes them: set `removeOnFail: false`, or `{ age, count }`, to keep them. Worker options had no such default and are unchanged.
- **A typed error keeps its status when a Postgres error is its cause** `typed-error-over-pg-cause` (`@venizia/ignis-kernel`): `getError({ message, statusCode: 409, messageCode, cause: pgError })` was answered as the Postgres error (`400`, or the retryable `409`), so its status and code were lost. An error thrown with `getError` is now answered as it says; the Postgres mapping applies to errors that are not typed this way, a bare driver error or an ORM wrapper around one. `getError({ message, cause: pgError })` without a `statusCode` is typed too and answers `getError`'s default `400`; a wrapped `40001` or `40P01` used to give the retryable `409`, so set the status you want.

## Security
- **A metadata address opens only by its own literal** `trusted-origin-metadata` (`@venizia/ignis-helpers`): `169.254.169.254` and its kin (`100.100.100.200`, `fd00:ec2::254`, link-local, and their IPv4-mapped, NAT64 and 6to4 spellings) are reached only when the trusted origin's host is that exact IP and the chain was trusted from the first url. A trusted host name that resolves to one, or a redirect from an untrusted hop to one, is refused.
- **A url with credentials is refused on a trusted origin too** `trusted-origin-credentials` (`@venizia/ignis-helpers`): `http://user:password@vault/` has a trusted origin but is still refused. Send credentials in a header.
