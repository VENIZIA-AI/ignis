`@venizia/ignis-helpers` sits one layer above `inversion` in the dependency chain (`dev-configs -> inversion -> {filter, helpers} -> kernel -> core`) - it depends on `inversion` alone, and `boot`, `kernel` and `core` all depend on it. It is a production-ready utility library designed to integrate with the IGNIS IoC container, and ships a dual CJS + ESM build. See the full catalog at [helpers catalog](/reference/helpers.md).

## Module map

`src/modules/` (verified against source) contains: `base` (the shared `BaseHelper`), `cron`, `crypto`, `env`, `error`, `logger`, `network`, `pool`, `queue`, `redis`, `retry`, `secrets`, `slug`, `socket` (Socket.IO and WebSocket subfolders), `storage`, `temporal`, `tree`, `uid`, and `worker-thread`. Highlights:

- **logger** - follows the house tiering: `common/` holds the provider-agnostic `ILogger` contract, `TLogLevel`/`LogLevels`, and `LoggerFormats`; `base/` holds `AbstractLogger`/`BaseLogger` (scope/prefix/DEBUG-gate/`.for()` plumbing shared by every provider); `winston/` is the self-contained built-in provider (`WinstonLogger`; `formats.ts` holds `WinstonFormatFactory`, `logger-factory.ts` holds `WinstonLoggerFactory`, `define.ts` re-exports their static methods as the historical function names; its own `common/`, `formatters/`, `transports/`); `hf/` is the separate `HfLogger` pipeline - `HfLogger extends AbstractLogger` and implements
`ILogger` (string methods backed by a bounded FIFO encode cache, args formatted through
`formatLogMessage` so nothing is ever dropped; the legacy bytes hot path survives as an overloaded
`log(level, string | Uint8Array)`), writes entry-layout-v2 records (per-entry length bytes, no NUL
padding or stale tails) into a plain, lazily-allocated `ArrayBuffer` ring (`SharedArrayBuffer`
dropped - the design is explicitly single-thread, so nothing is allocated at import time), and
drains through `HfLogFlusher` (`{ sink?, filePath?, batchSize? }`, batched yielding drains,
unref'd `start()`, `stop()`, exact per-batch `dropped` lap accounting). `LoggerFactory.getLogger()` returns `ILogger` and the factory is the ONLY provider-selection point - callers never see which class backs the instance (`Logger.get(scope)` remains the winston-concrete path; custom-backed wrappers are NOT cached). Formatting is two-stage: shared prep on the logger, per-transport assembly - color on console only, files/UDP stay ANSI-free. Console color is ENVIRONMENT-GATED by `resolveLoggerColorize()`: `APP_ENV_LOGGER_COLOR` wins, then a non-empty `NO_COLOR` forces off, then `NODE_ENV` outside `Environment.DEVELOPMENT_ENVS` forces off - the same fail-closed boundary the error sanitizer uses. It returns `boolean | undefined`, and `undefined` means NO framework opinion: winston (which has no terminal detection) reads it as on, and the pino path forwards nothing so `pino-pretty`'s own `isColorSupported` still decides. `ICustomLoggerOptions.colorize` overrides all of it. Note `bun test` runs under `NODE_ENV=test`, which is NOT a development env - a test asserting colorized output must pass `colorize: true` explicitly. `APP_ENV_LOGGER_LEVEL` (default `debug`) is the logger-level floor; daily-rotate-file transport is opt-in via `APP_ENV_LOGGER_FOLDER_PATH`. Provider REGISTRATION: `LoggerFactory.use({ provider })` (swap-on-use delegating wrappers - even module-level loggers captured at import follow it; wrapper cost ~0ns measured; delegates resolve LAZILY at the first log call). SINGLE-PROVIDER LOADING: exactly one provider is ever loaded - the registered one, or the winston default lazily required behind a `createRequire` boundary in `factory.ts` (bundler-opaque). Both providers are SUB-PATH ONLY: `WinstonLogger`/`Logger`/`defineCustomLogger`/`DgramTransport`/formatters at `@venizia/ignis-helpers/winston`, `PinoLogger` at `/pino`; the root barrel is provider-free (guard test `no-eager-winston-import.test.ts`). winston/winston-transport/winston-daily-rotate-file and hono are OPTIONAL peers - apps on the winston default must install them; compiled binaries must register a provider explicitly (class reference bundles it); the registration lives in a `globalThis` slot (`Symbol.for('ignis:logger-provider')`) so the ESM copy an application imports and the CJS copy core requires share one provider. `Environment.ambient` is the bundler-safe `NODE_ENV` read (destructured, never folded by `bun build`); `secrets/factory.ts` imports its providers statically because a dynamic `import()` of our own module made bun emit the root barrel with undefined exports - see [Gotchas](/conventions/gotchas.md). `ApplicationLogger` is the provider-following facade; the lowercase `applicationLogger` instance was REMOVED (migrate to `ApplicationLogger.get(scope)`). Secret redaction has a kill-switch: `APP_ENV_LOGGER_DO_REDACT=false` (that literal only - fail-closed, per-call read) turns `redactSecrets`/`redactUrlCredentials` into pass-throughs for local debugging; never in production. `formatLogMessage` projects arguments PER PLACEHOLDER: `%s` inspects a redacted copy at `APP_ENV_LOGGER_INSPECT_DEPTH` (default 5), `%j` goes through `toJsonSafe` under the same depth cap - `JSON.stringify` answers `[Circular]` for the WHOLE argument when one cycle sits anywhere inside it, so one live transaction or connector handle used to erase every other field. The structural pass in `toJsonSafe` is unconditional; only the key masking follows the kill-switch. `%o`, `%O` and arguments with NO placeholder ARE redacted too - they go through `redactSecrets` at `depth + 2` and stay OBJECTS, so `util.formatWithOptions` still renders them the way the placeholder means (pre-inspecting them would make `%o` print a quoted, escaped string instead of an object).
- **redis** - `AbstractRedisHelper` is the shared data API; `RedisSingleHelper`, `RedisClusterHelper`, and `RedisSentinelHelper` implement it for the three topologies, selected via `createRedisHelper({ mode })`. `ioredis` is an optional peer loaded by name in each constructor (lazy since helpers 0.2.0-37; every `@venizia/ignis` 0.2.0 prerelease declares `^0.2.0-N`, which admits -37, so a FRESH install of any of them - not just -45+ - gets lazy ioredis), so all three take `module?: typeof import('ioredis')` through `IRedisModuleOption` (`createRedisHelper` passes it through): a `bun build --compile` binary has no `node_modules`, and without the option or `ModuleUtility.register({ modules: { ioredis } })` its first client throws `[ModuleUtility.loadSync] ioredis is required ...` - proven by a real compiled binary in `__tests__/redis/compiled-binary.test.ts`. Consumers should depend on the `IRedisHelper` interface and use `isRedisHelper(value)` for identity checks - a `Symbol.for` brand, never `instanceof`, which is `false` between two installed copies of this package.
- **queue** - `BullMQHelper` (Redis-backed queue/worker pair), `SequentialQueueHelper` (in-memory, generator-based, state machine `WAITING -> PROCESSING -> LOCKED -> SETTLED` from `QueueStatuses` in `internal/sequential/common/types.ts`), `MQTTClientHelper`, and a Kafka bundler.
- **pool** - a generic, engine-neutral object pool: `AbstractPoolHelper<T>` owns state and a single re-entrancy-guarded dispatch loop pairing idle resources with waiting acquirers; `BasePoolHelper` is the concrete, callback-configured subclass. The waiter queue is backed by an internal `HfQueueHelper` (O(1) FIFO, no array shift/splice on the hot path).
- **storage** - `BaseStorageHelper` abstract base; `BunS3Helper` and `DiskHelper` implement `IStorageHelper` (`MemoryStorageHelper` is a separate in-memory keyed container, not one of them). `MinioHelper` was removed and then restored the same day, so it ships again - both it and `IMinioHelperOptions` carry `@deprecated`, it is reachable only through `@venizia/ignis-helpers/minio`, and `minio` stays an optional peer. The deprecation names the replacement: `BunS3Helper` reaches MinIO over the same S3 API and adds presigned URLs, tagging and byte ranges, so the sub-path goes once that path has settled. Every validator takes an options object, and every one of them names its bucket and its object: `isValidSegment({ segment })`, `isValidBucketName({ bucket })`, `isValidObjectKey({ object, maxDepth })`, `getMimeType({ filename })` - a single positional parameter is not an exception to that rule. `isValidKeyPath({ path, maxDepth })` is the protected rule shared by `isValidObjectKey` and the folder check inside `upload`. `upload` checks the original name by what it becomes: with no `normalizeNameFn` it IS the key and gets `isValidSegment`; with one it is metadata and gets the protected `isValidOriginalName` (not blank, <= 255 chars, no `\p{Cc}`/`\p{Cs}` control char or lone surrogate), while every resolved key still gets `isValidObjectKey` before the first write - so a multi-file upload is all-or-nothing on names, not per file. `copyObject` (`BunS3Helper`) builds `x-amz-copy-source` with `buildCopySource` (per-segment SigV4 encoding, `/` kept literal): Bun refuses a non-Latin-1 header value outright, and S3 URL-decodes the header and splits `?versionId=` off it, so a raw `+ % ?` in a key names a different object. `presignPost`'s `postURL` is built from the same `objectEndpoint` `pathPrefix` every object call uses - the bucket sits in the host (virtual-hosted addressing) or the path (path style addressing), never both; it used to be both under `virtualHostedStyle: true`. `MinioHelper` RFC 2047-encodes the `originalName`/`normalizeName` metadata values outside printable ASCII - a header cannot carry them raw. `createContentDispositionHeader`'s `filename*` carries the real UTF-8 name; `filename` stays the printable-ASCII fallback. `filename*` replaces every control (`\p{Cc}`), format (`\p{Cf}` - bidi overrides, zero-width space) and lone-surrogate (`\p{Cs}`) character with `_`, EXCEPT U+200C/U+200D (zero-width non-joiner/joiner), which stay: they build emoji ZWJ sequences and join letters in Persian and other scripts, and reorder nothing. `ContentTypeTable` covers the common office formats (xlsx, xls, docx, doc, pptx, ppt, odt, ods) alongside the types it already had. A missing object throws the catalogued `core.storage.object_not_found` carrying a 404; anything else propagates untouched, so a storage outage is never reported as a missing file. `DiskHelper` resolves every read and delete through a containment check - name validation plus an assertion that the resolved path stays under the bucket, because the first is a rule about input and the second is a fact about the result. `presignPut`/`presignGet`/`getObjectTags`/`replaceObjectTags` are concrete on the base and throw by default, naming the class and method; `BunS3Helper` implements all four and tags over signed HTTP (`GET`/`PUT ?tagging`, hand-parsed XML) because Bun's `S3Client` exposes no tagging method. `parseMultipartBody` returns `{ files, fields }`: it used to return `IParsedFile[]` and `continue` past every string entry, so a text field posted beside an upload vanished with no error. It reads the body through `readFormBody` (`utilities/form-body.utility.ts`), which maps a parse failure to `RequestBodyErrors.BODY_MALFORMED` (`400 core.request.body_malformed`) instead of the runtime's own error. `readFormBody` is on the root barrel and on `/core`; its error definition, `RequestBodyErrors`, is `/core`-only - the root barrel's `export *` there was narrowed to the one function, so a consumer names the kernel's `RequestErrors.BODY_MALFORMED` (the same object) instead. `presignPut` left `client.presign` for the same reason: its options are a method and an expiry, so `tagging` and `contentLength` - which have to be INSIDE the signature to exist at all - are signed by a hand-built query-signed SigV4 URL (`buildPresignedUrl`), verified against the signature AWS publishes for its documented example. `publicEndpoint` exists because `host` is inside every signature, so a URL signed against an internal endpoint cannot be rewritten afterwards. `getObjectStream` returns a web stream with an optional byte range - S3 turns the range into a ranged GET. `writeStream` is the other direction and is on the interface so a large body never lands in this process; it takes the same folder-depth rule as `upload` (`maxFolderDepth`, defaulting to `DEFAULT_MAX_FOLDER_DEPTH`). The base implementation buffers, which is exactly the thing to avoid, so a backend whose transport accepts a stream overrides it. `upload` and `removeObjects` run through `executePromiseWithLimit`, never an unbounded `Promise.all`.
- **crypto** - `BaseCryptoAlgorithm` with AES (`aes-256-cbc`/`aes-256-gcm`), RSA and ECDH implementations, including file encrypt/decrypt. `normalizeSecretKey` derives the key with PBKDF2-SHA256 (memoised per secret+salt+iterations) and returns a `Buffer`; the old pad-or-truncate derivation is gone. The salt and iteration count default to `DEFAULT_KDF_SALT`/`DEFAULT_KDF_ITERATIONS` (a constant baked into every deployment - it stops a bare dictionary lookup, not a table precomputed against that exact value) but both are overridable: `AES.encrypt`/`decrypt` accept `opts.kdfSalt`/`opts.kdfIterations`, which must match on both sides of a round trip. A supplied `kdfSalt` is validated to be at least 16 UTF-8 bytes (`MINIMUM_KDF_SALT_BYTES`, the NIST SP 800-132 minimum) and throws via `getError` otherwise. Omitting both options reproduces the shipped default byte-for-byte - the default can never change without breaking every ciphertext already encrypted under it, so it never will; per-deployment isolation is opt-in via `kdfSalt` instead. `LegacyAES` does not accept either option: its key derivation (`normalizeSecretKeyLegacy`) is padEnd/truncate, not PBKDF2, so there is no salt to override. AES ciphertext is a self-describing envelope - `[version(1)][idLen(1)][id][iv(16)][authTag(16, gcm)][cipher]` - so `secret` accepts a keyring (`{ id, secret }[]`, encrypt uses entry 0, decrypt resolves the envelope's id) and a key rotates by prepending an entry rather than re-encrypting. `decrypt` takes no `iv`: the envelope holds it, and `IAESDecryptOptions` omits the field so supplying one fails to compile. `LegacyAES` reproduces the pre-PBKDF2 derivation and layout for data written by an earlier IGNIS; the two formats NEVER cross-decrypt and nothing falls back automatically. `IPayloadCipher` is the string-in/string-out slice both satisfy - the bearer-token services take it as `cipher`, which is how an application keeps tokens issued before the change readable. `Hash` covers digests and HMACs; it does not implement `ICryptoAlgorithm` because a digest has no `decrypt`. `digest({ message, opts? })` takes no secret at all, and `hmac({ message, secret, opts? })` requires one and throws if it is empty - so a caller can never get HMAC's silent unkeyed fallback. `HashAlgorithms` (`md5`/`sha1`/`sha256`/`sha384`/`sha512`) and `HashOutputEncodings` (`hex`/`base64`/`base64url`) are const-classes with `TConstValue` types, the repo's standard shape for an enumerable string set. MD5 and SHA1 stay only for wire-protocol compatibility (VNPay checksums); both are documented as unfit for security decisions. The old `hash(text, options)` free function in `utilities/crypto.utility.ts` is removed entirely - not deprecated, gone, file and all - along with its plaintext-passthrough bug; every caller must migrate to `Hash` (see the 2026-08-30 changelog for the call-shape mapping). `RSA.generateDERKeyPair({ modulus })` accepts any `modulus` with no lower bound (a test uses 1024, below the 2048-bit floor generally considered secure today) - known, not yet enforced.
- **network** - fetch-based HTTP client in the root barrel; TCP/TLS/UDP servers and clients; and `url-safety`, the SSRF guard. The guard is split in two so the decidable half stays browser-pure. `policy.ts` holds `UrlPolicy` - scheme allow-list, host allow-list, and a non-public-address classification covering loopback, RFC1918, carrier-grade NAT, the `169.254` cloud-metadata range and the `::ffff:` IPv4-mapped forms in both dotted and hex spelling - and decides a url with string and number work alone, so it rides `/core` and is gated by `make purity`. Anything it cannot parse answers non-public: a guard that fails open on a string it cannot read is not a guard. `ingest.ts` is the `node:dns` half that `policy.ts` must never import: `UrlIngest.assertPublicHost` rejects when ANY resolved address is non-public (checking only the first walks into a host publishing one public record beside an internal one), `assertReachableUrl` runs shape then network, and `fetchGuarded` follows redirects BY HAND (`redirect: 'manual'`) so every hop is re-checked. Defaults are safe by default: HTTPS only, no private address, three hops, ten seconds, ten megabytes. A refusal is the catalogued `core.url_safety.url_refused`, and `isUrlRefusedError` exists so a retrying caller can tell a permanent refusal from a timeout. A DNS-rebinding window stays open by design - closing it means connecting to the resolved address and setting `Host` by hand, which no fetch API exposes.
- **uid** - four generators behind one door. `UuidHelper` (`uid/uuid/`, `getInstance()` cached per MODULE COPY, not in a realm slot - the facade holds no state, and a realm-wide slot would hand an older helpers version its instance and generators) is a THIN FACADE over three functions - `uuidV4`, `uuidV5`, `uuidV7`, each a closure from a `createUuidVN()` factory (the factory is the test seam: a private sequence to exercise the `getRandomValues` path; v7 shares one sequence per realm through a globalThis slot so CJS and ESM copies cannot interleave two counters) - all four published on their own subpath `@venizia/ignis-helpers/uuid` as well as through `./core`, because the class cannot be tree-shaken apart: measured with `bun build --target=browser --minify`, gzipped (2026-09-19, Bun 1.4.2), `uuidV4` alone is 409 B, `uuidV7` 572 B and `uuidV5` 8.7 KB, while the facade is 9.9 KB (v5 drags SHA-1, `getError` and a status-code table, and `reflect-metadata` behind inversion). ARDOR asked for this after measuring 10.2 KB for one `v4()` against a 7.7 KB brotli budget. `uuid-bundle-budget.test.ts` asserts the two small numbers (600 B / 800 B ceilings) so a re-export through the error module fails loudly; the control is real - making `v4.ts` import `getError` turns two of its three tests red. No generator is a class, so none extends `BaseHelper` - only the `UuidHelper` facade does. `v5` imports `getError` straight from `@venizia/ignis-inversion` and `HTTP` from the constants FILE, not either barrel - a consumer already importing inversion pays ~0 for the error path. The door: `v7()` for a database key, `v5({ namespace, name })` for a deterministic key such as an idempotency key, `v4()` for a random public identifier or token, plus `inspect({ value })` (version, and the creation time for a v7) and the static `isValid(value)`. Version chosen once per use, not once per call site - three call sites used to reach for `crypto.randomUUID()` directly, which browsers gate on a secure context. `v4` and `v7` are BOUND PROPERTIES, not methods: a forwarding method measured 40 ns against 32 for the native call it wrapped, a fifth of the cost for a wrapper. Every generator IGNORES ITS ARGUMENTS - `uuidV4`, `uuidV7`, `createUuidV4()`, `createUuidV7()`, `UuidHelper.getInstance().v4/.v7` - so point-free use is safe: `Array.from({ length: n }, uuidV7)`, `ids.map(uuidV4)`, hono `requestId({ generator: uuidV7 })` (guarded by `uuid-arguments.test.ts`). `v4` captures `crypto.randomUUID` ONCE and calls it with no argument (Node validates the argument, so `['a'].map` would throw), falling back to a pooled `getRandomValues` generator outside a secure context. `v5` reads the namespace case-insensitively and accepts the nil UUID (`UUID_NAMESPACE_PATTERN`, wider than `UUID_PATTERN` on purpose); it refuses (400) a name carrying a lone surrogate, which `TextEncoder` would turn into U+FFFD so two names would collide; a name too long for the 512-byte scratch buffer gets a buffer for that call only, so one huge name never pins its size. `v5` hashes with `Sha1Digest` (`uid/uuid/sha1.ts`, not exported): `node:crypto` is a builtin `make purity` refuses and `crypto.subtle.digest` is both asynchronous and secure-context-gated, so the digest is carried inline - the scratch padding buffer and the in-place word loads are why it costs 410 ns against 1509 for `uuid@14`'s v5, which answers the identical id. `UuidV7Generator` is GONE; `v7` is `createUuidV7()` - `getRandomValues` with a 12-bit per-millisecond counter that borrows the next millisecond on overflow or a backwards clock, so a burst embeds a timestamp slightly AHEAD of the wall clock, roughly one millisecond per 4096 ids. It NEVER uses `Bun.randomUUIDv7`, on any runtime: the pooled generator measured 43 ns against 58 native, and the native one reads its call arguments as `(encoding, timestamp)` - `Array.from({ length: 3 }, Bun.randomUUIDv7)` stamps ids at the 1970 epoch. Measured against `uuid@14` (median, Bun 1.4.2): v4 at parity (both call `crypto.randomUUID`), v5 395 ns vs 1163, v7 43 ns vs ~210. Never claim v4 is faster than `uuid@14`. `SnowflakeUidHelper` is a 70-bit Snowflake ID (48-bit timestamp + 10-bit worker ID + 12-bit sequence) with Base62 encoding, time-sortable. `OpaqueUidHelper` is the opposite trade, and the name states the property that matters: a Snowflake id is TRANSPARENT - `parseId()` reads back the exact millisecond it was minted and the worker that minted it - while nothing can be read out of an opaque one. It gives up the ordering for that, plus a chosen length, an optional `prefix`/`delimiter` pair of `{ enable, value }` toggles, and an alphabet from `UidAlphabets` (`CROCKFORD` 32, `BASE58` 58, `NO_VOWEL` 50, `BASE62` 62). `RequestIdGenerator` is a thin delegate over `UuidHelper.v4()` for correlation ids on both hosts. Which version to reach for: a database primary key is v7 (end to end it wins - on PGlite 200k text-PK inserts ran 11-36% faster, the index 27% smaller, `ORDER BY id` paging ~2.5x faster); a deterministic key from business data is v5, which is REPRODUCIBLE and therefore never a secret, and gives a stable key while the unique index is what enforces idempotency; a public identifier or token is v4, which carries no clock to correlate by.

  Three things `OpaqueUidHelper` refuses rather than doing quietly, each measured: **folding a two-case alphabet** (uppercasing `BASE58` yields 35 characters, not the 33 entropy predicts, because `I` and `O` come back - the pair it drops so `1` and `0` stay readable); **a delimiter drawn from the alphabet** (the id can no longer be split back apart); and **a delimiter with no prefix**. Sampling rejects out-of-range bytes rather than taking a modulo, which would favour the first 24 of 58 characters by ~1.5% invisibly. Entropy source is `crypto.getRandomValues`, which - unlike `crypto.randomUUID` - is not secure-context-only, so the helper works on plain http and in a browser Worker.

  `DEFAULT_UID_LENGTH` is **6**, an airline record locator. That is 2^30, and it works for airlines because a locator is scoped per carrier, recycled after the trip, and regenerated on conflict - not because 2^30 is large. Measured: ~4,600 ids for a 1% collision chance in one space, ~38,000 for 50%.

  `nextId({ prefix?, isAvailable?, maxAttempts? })`. `isAvailable` returns **true to ACCEPT** the drawn id and false to draw again - named for what it returns, since an `exists` callback whose `true` means "usable" is inverted polarity a reader gets wrong once. It returns `ValueOrPromise<boolean>`, and **the callback's return type decides `nextId`'s**: three overloads, so a sync check yields `string` and never allocates a promise, an async one yields `Promise<string>`, and a union yields `ValueOrPromise<string>`. The implementation runs synchronously until the FIRST pending verdict, then hands the rest to an async continuation. Bounded by `maxAttempts` (default 10) and throws rather than looping, because endless rejection means the space is full. Every argument is optional, `opts` included; `maxAttempts` WITHOUT `isAvailable` is refused rather than ignored, since nothing can reject a draw and the retry it configures cannot happen.

  An async check does NOT make an id safe - against a database it is a read then a write with a gap, and another request can take the id inside it. `isPromiseLike` is defined locally in `opaque.ts` rather than imported from `@/utilities/promise.utility`: that module imports the logger BARREL, which reaches `node:module` and would drag this browser-pure module out of `/core`.

  **This generator is probabilistic and no length changes that.** `prefix` PARTITIONS the space (`INV-7K2MQ9` cannot collide with `CUS-7K2MQ9`) so each entity type gets its own; it does not make an id unique inside that space. The column needs a unique index, and the insert must regenerate on violation - checking whether an id exists and then inserting races, so `executeWithRetry` around the INSERT with a fresh id per attempt is the shape, not a pre-flight lookup.
- **env** - `Environment` (reads `process.env.NODE_ENV`) and `ApplicationEnvironment({ prefix, envs })` for prefixed, typed environment access. The instance lives in the `Symbol.for('ignis:application-environment')` slot, so an ESM copy and a CJS copy share one map. A present-but-empty line - `KEY=`, or `KEY=   ` padded by a hand edit - is a pipeline that forgot to export the value, not a value: `get()` normalises it to `undefined` so `defaultValue` applies and `transform` is handed `undefined` rather than `''`. That runs ONLY when the caller supplied a `defaultValue`, so a read without one still returns `''` unchanged and no existing call site changes shape; `'0'` and `'false'` are values and are never normalised. Reads that cannot go through `get()` - module-load constants taken off `process.env` directly - apply the same rule by hand with `blankToUndefined(process.env.X) ?? fallback` (`utilities/parse.utility.ts`, on the root barrel and on `/core`), never `||`, which swallows `'0'` too. A blank `APPLICATION_ENV_PREFIX` is why this is a security rule and not a formatting one: `key.startsWith('')` is true for every name, so the helper stops filtering and copies the whole of `process.env` into its map.
- **tree** - pure in-memory tree utilities (`Map`/`Set`/arrays only, no Drizzle/DI/I/O), merged from two BANA copies (`GraphHelper` and a free-function module) that had each grown capabilities the other lacked. `common/types.ts` holds `ITreeNode<T>`/`INodeWithPath<T>` and the option interfaces; `walk.ts` has `TreeWalker` (static `walk`/`walkAsync`/`height`/`heightWhere`/`count`/`collectLeaves` - kept as two distinctly-named methods rather than one mode flag, since the return types genuinely differ, `void` vs `Promise<void>`); `builder.ts` has `TreeBuilder` (static `build`/`leaves`/`nonLeaves`/`print`). Three behaviors are preserved verbatim from production, on purpose: `shouldPrune(node, depth)` returning `true` still visits `node` - only its children are skipped from the queue, because a caller measuring depth to a boundary needs the boundary node counted; `build`'s cycle guard is a `seen` set keyed by `getKey` that SKIPS a repeated branch rather than throwing, because real hierarchies contain legitimate diamonds; `leaves({ includePath: true })` returns the root-to-leaf chain alongside each leaf so a caller does not pay for a second traversal.
- **RecursiveTreeSql** lives in `@venizia/ignis-connectors` (`relational/core`), not here - it emits Drizzle `SQL`, and this package deliberately carries no `drizzle-orm` dependency. See [connectors](/packages/connectors.md).
- **temporal** - `TemporalHelper` (`temporal/helper.ts`) does every calendar calculation once - `pattern.ts` is the one pattern dialect, `calendar.ts` the day/month arithmetic - on top of an `ITemporalAdapter` whose ONLY job is `getOffsetMilliseconds({ value, timeZone })` - the UTC offset a zone observes at an instant. The helper builds the wall clock from that (`calendar.ts` `wallClockAt`) and resolves a wall time itself (`instantsOf`: offsets a day before and after, each candidate checked), so no adapter can disagree on DST - dayjs and Luxon guess from TODAY's offset and resolved repeats by season when they did this themselves. `DayjsTemporalAdapter` reads ONLY `dayjs(x).tz(zone).utcOffset()`, which is host-independent - MEASURED 2026-09-23: 8.1M probes under hosts New York, Berlin, Sydney (2020-2030, 15-min steps, 7 targets), 0 wrong; ARDOR's own sweep 9,625 probes inside host gaps/repeats, 0 wrong. dayjs's own `format()` DOES move near host transitions (the control in `temporal.test.ts` 'and the host zone'), and the pre-redesign adapter read dayjs's fields, which is where a first reviewer's host-zone finding came from - do NOT reintroduce a host-zone caveat for the adapter, and never advise switching `TZ`. The one real dayjs flaw (ARDOR measured 2026-09-23): dayjs misreads a local-mean-time offset under one hour - London `-00:01:15` comes back `-75`, Madrid `-00:14:44` as `-884` - 20 zones off by up to 14.5 h before 1914; Saigon is fine (LMT over an hour). Documented, not worked around. Native and Luxon matched Temporal on 1,840,320 checks across 445 zones 1970-2037. ISO parse accepts an hour-only offset (`+07`) but only after a time (`2026-09-19-05` is refused); it also walks years < 1000 forward in 400-year Gregorian cycles because dayjs reads years < 100 as 19xx. The built-in adapters take the library as an ARGUMENT and this package imports no date library: `NativeTemporalAdapter()` (global `Temporal`, or `{ temporal }` from a polyfill; throws a clear error when neither exists - Node 24 has no global `Temporal` without `--harmony-temporal`, Bun has it), `DayjsTemporalAdapter({ dayjs })` (the caller's dayjs with `utc` + `timezone` extended - throws if `dayjs.tz` is missing), `LuxonTemporalAdapter({ DateTime })`. The library parameters are typed structurally (`ITemporalNamespace`, `IDayjsFactory`, `ILuxonDateTimeFactory`) so no library types ship. Values in: `Date` | epoch ms | ISO 8601 string; values out: `Date`. The zone is the constructor `timeZone` (default `'UTC'`, validated through `Intl`, a 500 when bad) or a per-call `timeZone` (a 400 when bad); the helper NEVER reads env. Units (`TemporalUnits`): `millisecond`..`hour` are elapsed time, `day`/`week`/`month`/`year` move the calendar in the zone and keep the wall time; months clamp (Jan 31 + 1 month = Feb 28); amounts must be integers; ISO weeks start Monday. Pattern tokens `YYYY YY MM M DD D HH H mm m ss s SSS Z ZZ`, `[literal]` text, bare `T` allowed; a run of one letter is ONE token, so `MMM`/`DDDD`/`ZZZ` and any other letter are REFUSED rather than split greedily (so a date-fns `yyyy` or a moment `MMM` fails loudly); `Z`/`ZZ` carry seconds when the offset has them (historic LMT, e.g. Saigon 1900 `+07:06:30`) and parsing refuses offset hour > 23, minute/second > 59; years 1-9999 only (every input and result is range-checked, so an overflowing `add` is a 400, never an Invalid Date); `YY` parses with the dayjs pivot (00-68 -> 2000s, 69-99 -> 1900s). DST: a skipped wall time resolves forward, a repeated one to the earlier instant; `startOf`/`endOf` for an hour or less treat each pass of a repeated hour as its own unit (latest start not after the value; the unit ends where the wall clock next shows the following value or this start again - Lord Howe's 30-minute shifts make a 90-minute or 30-minute hour); `add` of 0 returns the value unchanged. Published on `@venizia/ignis-helpers/temporal`, the root barrel, and `/core`; purity-claimed.
- **Dates before `temporal`** - `utilities/date.utility.ts` is DELETED: `isWeekday`, `getPreviousWeekday`, `getNextWeekday`, `getDateTz`, the re-exported `dayjs`, and the import-time `dayjs.tz.setDefault(APP_ENV_APPLICATION_TIMEZONE ?? 'Asia/Ho_Chi_Minh')` are gone, and `dayjs` is no longer a dependency. `sleep` stays (`utilities/sleep.utility.ts`); `hrTime` moved to `utilities/hr-time.utility.ts` (root barrel only - `process.hrtime` is Node-only, so it stays off `/core`). The TCP server helper's `storage.connectedAt`/`authenticatedAt` are `Date` now, not dayjs objects.

`BullMQHelper` loads `bullmq` through `ModuleUtility.loadSync` when it builds its queue or worker (in the constructor), not at import - so `@venizia/ignis/mail` needs `bullmq` only when the BullMQ executor is used; `SocketIOClientHelper` loads `socket.io-client` the same way in `configure()`, so a server using only the socket.io server helper never needs the client package. Both are therefore invisible to `bun build --compile`: a binary that uses them passes the peer through the typed `module` option (`IBullMQOptions.module?: typeof import('bullmq')`, `ISocketIOClientOptions.module?: typeof import('socket.io-client')`) or registers it once with `ModuleUtility.register`. `BullMQHelper.queueOptionsFor()`/`workerOptionsFor()` merge three layers in order: framework defaults, then `queueOptions`/`workerOptions`, then the fields the helper owns (`connection`, `concurrency`, `lockDuration`). A caller's option can never override the connection - it merges before the owned fields, not after. `isClusterClient()` duck-types a Redis Cluster client: a truthy `isCluster` or a `nodes()` method - never `instanceof`, since `ioredis` is an optional peer. A duplicated client, or one built from a second `ioredis` copy, still gets the `{queueName}` hash tag. `KafkaConsumerHelper.onStreamError`/`onReconnectError` each fall back to `onMessageError` when unset - a consumer that sets only `onMessageError` sees no change. Every member of `KafkaConsumerHelper` is `protected`, meant for a subclass to extend rather than fork. That visibility is not a stable contract between minor versions. `BaseKafkaHelper` itself matches: `connectedBrokers`, `onBrokerConnect`, and `onBrokerDisconnect` are `protected` too, for the same reason.

## Sub-path exports isolate optional peers

The root barrel needs no optional peer at load time: `ioredis` is loaded lazily by the Redis helpers
and `@hono/zod-openapi` is not a peer at all since the duplicate `ErrorSchema` moved to the kernel.
`src/__tests__/manifest/root-barrel-dependencies.test.ts` walks every static import reachable from
`src/index.ts`, fails on any bare package that is neither a dependency nor a peer - the gate that
would have caught the Atlas tarball dying on an import - and pins that neither `ioredis` nor
`@hono/zod-openapi` is reached.

Helpers that depend on an optional peer package are never re-exported from the root barrel - they are reachable only via their own sub-path, so importing `@venizia/ignis-helpers` never forces that peer into a consumer's bundle. Confirmed sub-path-only exports: `@venizia/ignis-helpers/socket-io`, `/bullmq`, `/mqtt`, `/bun-s3`, `/minio`, `/axios`, `/cron`, `/kafka`, `/hashicorp-vault`, `/dotenv-vault`, `/winston`, and `/pino`. Dedicated tests assert the root barrel never re-exports the axios fetcher, never loads winston, and never resolves pino.

`/common` is a sub-path of a different kind: it does not isolate a peer, it exposes the surface that is already browser-safe. The root barrel is `export * from './modules'`, so reaching one constant through it drags 14 node builtins into a browser bundle (measured 2026-09-18: `node:fs`, `node:net`, `node:tls`, `node:worker_threads` and ten more; the only packages it loads statically are `@venizia/ignis-inversion`, `reflect-metadata` and `zod` - every optional peer is lazy). `@venizia/ignis-helpers/common` carries `HTTP`, `TConstValue`, the constant and redaction tables, and resolves to only `@venizia/ignis-inversion` and `reflect-metadata` with zero builtins. The error layer is deliberately NOT re-exported there: `getError`, `ApplicationError`, `ErrorScopes` and the `TError*` types live in `@venizia/ignis-inversion`, which is browser-clean on its own, so a browser consumer imports them from inversion directly rather than through a second path. This sub-path and `/core` are guarded together by the repo-root purity gate described below.

`/core` also carries the HTTP layer - `NodeFetchNetworkRequest`, `NodeFetcher`, `BaseNetworkRequest`.
It could not before: `node-fetcher.ts` imported `node:querystring` for ONE `stringify` call, which
kept the whole network layer out of a browser bundle and pushed every browser-facing connector into
writing its own HTTP - which is exactly what `connectors/http` started out doing. The function is
written out now, diffed against node across 22 cases with zero mismatches. `URLSearchParams` was not
the answer: it disagrees on four, including turning `undefined` into the STRING "undefined" and
collapsing `a=1&a=2` into `a=1%2C2`.

`parseContentDisposition` is the reading half of `createContentDispositionHeader`. It handles the
RFC 5987 `filename*` form, which a parser that splits on `filename=` returns percent-encoded - the
wrong answer for any non-ASCII filename.

`@venizia/ignis-helpers/core` is a separate isomorphic surface alongside `/common`, not a superset of it - the two are disjoint, sharing zero exports. `/core` is built from `src/core.ts` re-exporting each module by its **leaf** path rather than its barrel (a barrel is how every purity leak in this package has travelled - the logger barrel pulls `node:module`, the http-request barrel pulls `node:querystring`). It carries `BaseHelper`, the error layer (by name, from inversion), `uid` (`SnowflakeUidHelper`, the uuid functions), `temporal` (`TemporalHelper` and the three adapters), `pool` (`AbstractPoolHelper`/`BasePoolHelper`), `HfQueueHelper`, the `ILogger`/`ILoggerProvider`/`TLogLevel`/`LogLevels` contract, and the fetcher interfaces (`IFetchable`, `AbstractNetworkFetchableHelper`) from the fetcher's leaf file, never the `http-request` barrel. It also carries `EnvironmentNames` - by name, never `export *` from `./modules/env`, whose barrel drags `Environment` and `applicationEnvironment` and their `process.env` reads - the url-safety pure half (`UrlPolicy`, `UrlSchemes`, `UrlSafetyDefaults`, `IUrlSafetyPolicy`; `UrlIngest` stays out, it needs `node:dns`), `SlugHelper`, and `TreeBuilder`/`TreeWalker` with the tree types. `retry` follows the same leaf-path rule even though its own module barrel (`modules/retry/index.ts`) is browser-clean: `RetryHelper` comes from `modules/retry/helper`, `RetryBackoffStrategies`/`RetryJitterModes` from `modules/retry/common/constants`, and `IRetryBackoffOptions`/`IRetryContext`/`TRetryBackoffStrategy`/`TRetryJitterMode` from `modules/retry/common/types` - never `modules/retry` itself. Exporting the class carries all nine retry operations into the browser as statics, including `RetryHelper.runWithTimeout`, `RetryHelper.isRetryTimeoutError` and `RetryHelper.computeBackoffDelayMs` - there is no module-level function alias, `RetryHelper` is the only surface. It also carries the pure value utilities - `toBoolean`, `int`, `toCamel`, `keysToCamel`, `blankToUndefined`, `executeWithPerformanceMeasure`, `ProjectRootRegistry`, and `BuildInfoRegistry` with `IBuildInfo`/`TBuildInfoRecord` - each exported individually rather than by widening the `./utilities` barrel, which carries node-only siblings (`module.utility.ts`, `request.utility.ts`) and so can never become a sub-path itself. `ProjectRootRegistry` is the `globalThis`-slot half of `ModuleUtility.setProjectRoot()`/`getProjectRoot()`, which delegate to it - a purity-restricted host (`@venizia/ignis-worker`'s `WorkerApplication`) reaches it through `/core` without pulling in `ModuleUtility`'s own `node:path`/`node:module` imports. Three further re-exports are type-only and therefore free: `AESAlgorithmType`, `IPayloadCipher`, and `IRedisHelper` are erased at compile time, so the crypto algorithms and the ioredis-backed helper they describe stay out of the runtime surface. `ErrorSchema`/`TErrorResponse` are not in helpers at all - they live in `@venizia/ignis-kernel` beside the REST layer that needs `@hono/zod-openapi`. `ioredis` is an optional peer: the Redis helpers load it with `ModuleUtility.loadSync` in the constructor, so the root barrel loads neither it nor `@hono/zod-openapi` (pinned by `root-barrel-dependencies.test.ts`).

Both browser-facing sub-paths are enforced by one repo-wide gate, not by anything local to this package: `scripts/purity/{probe,manifest,cli}.ts` at the repo root. `PURITY_MANIFEST` is DERIVED, never hand-listed: `PURITY_CLAIMS` names the packages that claim browser purity - `inversion`, `filter`, `helpers` restricted to `./core`, `./common`, `./uuid` and `./temporal`, `kernel`, `core-worker`, `connectors` - and `deriveEntries` expands each into one row per published export condition by reading that package's own `exports` map, so a renamed sub-path fails the manifest instead of silently dropping its row. `connectors` carries pinned `impure` waivers (the engine clients, which speak a wire protocol and can never run in a tab) and one `external` (PGlite, whose universal build measures its packaging rather than ours). Each claim is run by `make purity-inversion` / `purity-filter` / `purity-helpers` / `purity-kernel` / `purity-connectors` / `purity-core-worker` (or `make purity` for all of them), wired into CI immediately after lint; the packages with no claim have explicit no-op targets rather than missing ones.

The probe bundles the BUILT entry for `target: 'browser'`, which means two things worth knowing before trusting a green result. First, build success is not a purity signal: `bun build --target=browser` never fails on `node:fs` - it stubs the unpolyfillable builtins to an empty object and inlines the polyfillable ones - so it exits 0 either way and the specifier never survives into the output text. The signal is the `--metafile` module graph, the only place the specifier is preserved, matched against `node:module`'s own `builtinModules` list so the bare `fs` spelling counts too. Second, Node globals survive verbatim into a browser bundle, so the probe also runs anchored patterns for `process.`, `__dirname`, `__filename` and `createRequire` over the bundled text - anchored because a bundle legitimately contains identifiers like `processQueue`. `--env=disable` is mandatory: Bun otherwise inlines `process.env.NODE_ENV` as a compile-time constant and erases the very read the gate exists to catch, with the erasure depending on whatever `NODE_ENV` the probe happened to run under. Because the probe reads `dist`, build before you believe it - an empty `dist` gives a gate with nothing to measure.

`/core` never imports `LoggerFactory` as a value. `BaseHelper` reaches logging only through `logger/slot.ts` - a mutable slot `logger/resolver.ts` fills when it loads, which `LoggerFactory`'s module does. `logger` is an ACCESSOR: the first read resolves it and pins it as an own, NON-ENUMERABLE property (`Object.defineProperty`, writable), so later reads are a plain property read and it never appears in `Object.keys`, JSON or a spread; `helper.logger = x` still works before and after the first read; a subclass cannot redeclare `logger` as a field (TS2610). A logger read while the slot is empty is a deferred logger: it writes to the console, then hands every call to the real resolver the moment one is installed - children taken with `.for()` included - so nothing needs reconstructing. The deferred logger hands each line to the LEVEL METHOD of the real logger (never `log()`), so the provider's `DEBUG` gate applies; `BaseLogger.log` and `HfLogger.log` gate `debug` too. Reading `logger` off a prototype (reflection) returns a logger WITHOUT pinning it there - pinning on a prototype would shadow the getter for every instance. With no resolver in the whole import graph it prints ONE warning per process, Node/Bun only (`process.versions.node`), flagged on a `Symbol.for` global so CJS+ESM copies share it: ``[BaseHelper] Logging to the console - no logger provider is installed. Import `LoggerFactory` from `@venizia/ignis-helpers` at startup.`` (guarded by `helper-logger.test.ts`). Once the resolver module is loaded, `LoggerResolver`'s own wrapper re-reads the active resolver by generation, as before.

A sub-path is isomorphic only if its `.d.ts` graph is clean too, and that half is NOT automated. The purity gate bundles, and bundling erases types, so it cannot see a declaration reaching `axios`, `hono/jsx`, or the ambient `NodeJS` namespace - all three leaked into `/core`'s type graph, and `hono/jsx` separately leaked into `/common`'s (via `export * from './jsx'` in `common/index.ts`), before this package's types were audited by hand. Those known leaks are closed: `hono/jsx`'s `Child`/`FC`/`PropsWithChildren` are now re-exported from the root barrel directly (`export * from './common/jsx'` in `src/index.ts`, alongside `export * from './common'`) rather than through `common/index.ts`, the same shape `ErrorSchema` uses to stay off `/core`'s barrel while remaining reachable from the root. A type-graph gate closing this for good would run `tsc --noEmit` on a fixture consumer of each sub-path under a Worker-shaped `tsconfig` (`lib: ['ES2022', 'WebWorker']`, `types: []`, `skipLibCheck: false`): `types: []` removes the ambient `NodeJS` namespace a Node-flavored config supplies for free, and `skipLibCheck: false` stops a bad declaration silently widening to `any` - drop either and it passes for the wrong reason. Until then, a type re-exported from a peer with its own ambient globals is unguarded, so audit it by hand.

`ModuleUtility.getProjectRoot()` (default `process.cwd()`, set once by the application through
`setProjectRoot`, stored in the `Symbol.for('ignis:project-root')` slot so both module copies agree)
is the base of every `loadSync`/`assertInstalled` lookup: `createRequire(<projectRoot>/node_modules)`.
A process started from another directory sets `configs.projectRoot` instead of overriding
`getProjectRoot()` - to the directory that holds `node_modules` at RUN time. Never `__dirname` in a
`bun build --compile` binary (baked to the compile-time path; `import.meta.dir` is `/$bunfs/root`): a binary
leaves it unset or derives it from `process.execPath`. Pino transports resolve at the first log line, before
any application exists, so they follow the cwd, not this value.

The secrets family adds a second, bundler-facing rule. `createSecretsHelper` lives in the root barrel and reaches `node-vault` / `@dotenvx/dotenvx` at runtime, so those imports must go through `ModuleUtility.load({ module })` (in `utilities/module.utility.ts`), never a literal `import('node-vault')`. `Bun.build` resolves literal dynamic-import specifiers at bundle time - a literal anywhere reachable from the root barrel forces every consumer that compiles a binary to install the peer or list it in `external` (BANA had to exclude `node-vault` in every package's compile script before this was fixed). A plain `const s = 'node-vault'; import(s)` is not enough either: `minify: { syntax: true }` constant-folds it back into a resolvable literal. Only a specifier passed across a function boundary stays a runtime import; `src/__tests__/secrets/no-bundler-peer-resolution.test.ts` guards this (root-barrel bundle + resolution-spy + a positive control proving the spy fires on a literal import). `ModuleUtility.load` wraps a failed import in the standard `getError` install hint, so a missing peer reads the same whether reached through the factory or by constructing a provider directly from its sub-path. The trade-off: an app that uses a peer-backed provider **and** compiles a binary has no `node_modules` for the runtime lookup to resolve against, so it must ship the peer next to the binary, inject the client via the helper's options (`HashiCorpVaultHelper` takes `client`, `DotenvVaultHelper` takes `decode`), or hand the module over with `ModuleUtility.register({ modules })`. The app imports the peer statically (that import is what puts it inside the binary) and registers it before the consuming component binds; `load` and `loadSync` check the registry before touching the filesystem; `assertInstalled` ignores it unless the caller passes `allowRegistered`, which is correct only where `ModuleUtility` itself performs the load. This is the failure BANA's `identity` binary hit: it died at boot with `nodemailer is required` while `nodemailer` sat in its `package.json`, because nothing had put the peer inside the binary.

`register` is the FALLBACK, not the first answer: a global keyed by string depends on call order and types nothing. Prefer an options seam - every component that reaches an optional peer now has one: mail transports take `module`, the gRPC component takes `module` (`{ connect, protocol }`), the vault helpers take `client` / `decode`, the three Redis helpers take `module` (ioredis), `BullMQHelper` takes `module` (bullmq), `SocketIOClientHelper` takes `module` (socket.io-client), and the mail BullMQ executor takes `module` (bullmq) plus `redis.module` (ioredis). `register` has no first-choice call site left in the framework and is kept for consumers. Registering does NOT work wherever the consumer resolves the specifier itself: `pino.transport()` resolves its target inside a worker thread, and `GrpcRequestAdapter` uses its own `createRequire`. Both would be reported present by a registry-aware `assertInstalled` and then still fail - which is why `allowRegistered` defaults to false.

## Retry utilities

`src/modules/retry/` (`common/constants.ts` for `RetryBackoffStrategies`/`RetryJitterModes`, `common/types.ts` for `IRetryBackoffOptions`/`IRetryContext`, `helper.ts` for `RetryHelper`) exports two retry primitives, both options-object, both logger-aware, both static methods on `RetryHelper` - there are no module-level function aliases, `RetryHelper` is the only surface:

- **`RetryHelper.executeWithRetry`** - the general-purpose retrier: retries `execution` on a *thrown error*, races each attempt against an optional `perAttemptTimeoutMs`, and stops at `maxAttempts`, an elapsed `maxTotalMs` budget, or a `shouldRetry` classification hook returning `false` (default: retry every failure). On exhaustion it rethrows the LAST error, after exactly one `logger.warn`. Backoff strategy defaults to EXPONENTIAL from a 250ms initial delay, capped at 30000ms, with FULL jitter (`RetryBackoffStrategies`/`RetryJitterModes` also offer FIXED, LINEAR, SCHEDULE and NONE, EQUAL).
- **`RetryHelper.executeWithRetryUntil`** - the predicate-driven sibling: retries while `until(result)` returns `false`. Built for read-after-write staleness (replica lag, async indexing). The rules:
  - A thrown error is never retried - it propagates immediately. Only wrap idempotent reads.
  - On exhaustion it returns the LAST result with one `logger.warn` - never an error.
  - `maxTotalMs` only gates whether a NEW attempt may start; an in-flight execution always completes. A non-positive value means "no retries" - one execution still runs. It is deliberately NOT forwarded to `executeWithRetry`, where the same name means a per-attempt timeout.
  - An aborted `signal` REJECTS the call. `maxAttempts` below `1` throws before any execution runs.
  - Internally a plain loop over `computeBackoffDelayMs` + the signal-aware sleep - NOT a wrapper around `executeWithRetry`. The two retry on opposite triggers; sharing the loop would mean tunnelling the predicate through the error channel.
  - Primary consumer: `AbstractRepository.executeReadWithRetry` in `@venizia/ignis-kernel` - see [Repository hierarchy](/architecture/repository-hierarchy.md).

## Gotcha: Kafka and compiled binaries

`@platformatic/kafka` breaks `bun build --compile` in two independent ways, both by resolving something at runtime that the bundler cannot see. Both kill the process during module-graph load, before any IGNIS error handler exists. Register `platformaticKafkaPlugins()` (from the `/kafka` sub-path) in the app's own `Bun.build()` call - the `bun build --compile` CLI accepts no plugins.

- `platformaticWasmPlugin()` - `@platformatic/wasm-utils` reads `native.wasm` off disk at module load, which `--compile` never embeds. The plugin redirects the import to the `/bundled` entrypoint with the wasm inlined. Symptom: `ENOENT ... /$bunfs/dist/native.wasm`.
- `platformaticRequirePlugin()` - since 2.8.0, `registries/confluent-schema-registry.js` does `const AjvDraft04 = require('ajv-draft-04')` and `const draft06MetaSchema = require('ajv/dist/refs/json-schema-draft-06.json')` at MODULE SCOPE, through `createRequire(import.meta.url)`. `dist/index.js` re-exports that file, so importing anything from the package runs both lines. The plugin rewrites each module-scope `const X = require('spec')` into a static import at bundle time. Symptom: `Cannot find package 'ajv-draft-04' from '/$bunfs/root/index.js'`.

Three constraints on `platformaticRequirePlugin` that the code alone does not explain:

- **The injected binding is `const X = <alias>;` - never `<alias>?.default ?? <alias>`.** The draft-06 meta schema JSON carries its own top-level `default` key (`{}`), so unwrapping silently replaces the meta schema with an empty object. The binary still boots and the registry still constructs; draft-06 validation then fails with `no schema with key or ref "http://json-schema.org/draft-06/schema#"`. A default import already yields `module.exports` for CJS, so no unwrap is needed. Guarded by `bundler.test.ts` - the compiled probe fetches a draft-06 schema through a local stub registry.
- **The pattern is anchored to `^const ... ;$`**, so the lazy `return require('protobufjs').parse;` inside a method never matches. `SKIPPED_SPECIFIERS` (`protobufjs`, `@node-rs/crc32`) is defence in depth: both are optional peers, and a static import would break builds that do not install them.
- **No match returns `undefined`**, so the plugin is an inert no-op once upstream fixes this. An unresolvable specifier fails the BUILD with Bun's own error rather than dying at runtime - that is the point of hoisting.

## Duration units and conversion

`src/common/constants/duration.ts`, on the browser-pure `/common` sub-path. Ported from BANA, keeping
`toMilliseconds`'s contract so BANA migrates by changing an import. Left behind on purpose: BANA's
`LABELS` (English/Vietnamese display strings, and they pull its `INameI18n`) and `NearExpiryThreshold`
(business logic).

- **`DurationUnits`** - eight canonical names, `SCHEME_SET`, `isValid`. `TDurationUnit` is the union;
  `IDuration` is `{ unit, value }`.
- **`DurationAliases`** - a const class whose UPPER_CASE member names ARE the accepted spellings
  (`MS`, `WK`, `DAYS`, `MO`). `resolve()` reads a written unit into its canonical name. `M` is MINUTE
  and `MO` is MONTH - there is no single-letter month.
- **`DurationMultipliers`** - `BY_UNIT`, plus `toMilliseconds`, `fromMilliseconds`, `convert`,
  `parse('30d')` and `parseToMilliseconds`. Every one answers `null` rather than throwing, so a caller
  that wants an error raises its own with its own context. `toMilliseconds` rounds; the other two do
  not, because rounding out would lose a 36-hour window asked for in days.

Three constraints worth knowing before editing it:

- **A month is 30 days and a year 365, nominal.** They size a WINDOW - a grace period, a cache TTL -
  and must never compute a calendar date. Pinned by a test so a "fix" has to be deliberate.
- **The alias table is DERIVED from `DurationAliases`**, never hand-listed beside it. Reading the const
  class directly is 5x slower and would need `name`/`length`/`constructor` guarded out of the lookup.
- **`resolve` tries the input as given before normalising.** The lookup costs ~1ns either way;
  `trim().toUpperCase()` costs ~55ns, so a canonical `'day'` is ~2ns and only a messy `'  Days '` pays.

## Conventions

Every helper extends `BaseHelper`, which gives it `scope`, `identifier` and a scoped `ILogger` (`this.logger.for('methodName').debug(...)`, resolved on first read - see the `/core` logger paragraph) - and nothing else. A helper that owns a lifecycle implements `IConfigurable`'s `configure(opts?)` itself (`common/types/injection.ts`); it is not inherited. All public functions take options objects, never positional arguments. `RuntimeModules.detect()` (and `.isBun()`/`.isNode()`) gate any runtime-specific branch.
