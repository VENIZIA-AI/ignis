How to work in the IGNIS repository. **This file is routing**: the rules and the facts live where it
points. The one block of rules it carries is generated by `vulcan sync` and only names the ones
sessions drop most.

This is the **only tracked instruction file**. Tool-specific files (`CLAUDE.md`, `GEMINI.md`, ...)
are gitignored adapters that point at this one, written per developer by VULCAN:

```bash
make vulcan-sync      # = bun x --no-install vulcan sync
```

## Rules that must not be skipped

Full text, cited by ID: `node_modules/@venizia/vulcan/base/rules.md` (V-*) and `.agents/rules.md`.

- V-W-01: this project: `on-user-word` - Git writes happen only on the user's word, in this conversation.
- Pack `venizia` (`node_modules/@venizia/vulcan/base/packs/venizia.md`): this project follows it - V-B-05, V-B-09, V-C-07, V-C-08, V-C-20.
- V-W-02: Never write to a database. Write the migration file, hand over.
- V-W-03: Never deploy or hot-apply (kubectl apply, docker compose up, restarts).
- V-W-06: Approval has a card. Shared writes follow four action classes.
- V-B-08: Scratch and temporary files go in `.agents/local/tmp`, never /tmp or the scratchpad folder a tool offers. Claude Code sets `TMPDIR` to it; elsewhere `export TMPDIR="$PWD/.agents/local/tmp"` from the project root.
- P-09: Carry the minimap in every status message.
- P-10: Report like a colleague who was away, not like a log.
- B-03: Extends V-B-03. A step that failed or was skipped is reported as such, never folded into a pass.
- B-05: A downstream suite tests `dist`, not `src`.
- P-05: Crosscheck the downstream project before calling a framework change finished.
- P-15: Empty is not evidence of absence, and plausible is not evidence of correct.
- W-02: Never `git checkout`/`git restore` a file that carries uncommitted edits.

## Atlas

The `atlas` MCP server holds the real code and docs of: ignis (this repository).
Look facts up there before you answer or write from memory (V-P-07):
`symbol` before you use an export (signature, import path, source line); `search`, then `get`, for how something works or which convention applies; `version` or `changes` for a release or an upgrade.

## Two homes for everything

Nothing lives in two places. Every piece of project information has exactly one home:

- **`.agents/`** - what agents read: the rules, the knowledge bundle and the okf renderers.
- **`docs/wiki/`** - the human-facing VitePress site: guides, references, changelogs.

Source code is the ground truth for both. When prose and code disagree, the code wins and the prose
is a bug (P-03). The wiki and the bundle are separate audiences; never conflate them (V-C-13).

There are **no per-package agent files** - a package carries no local `CLAUDE.md`. Read its concept
in the knowledge bundle instead.

## The knowledge bundle (`.agents/knowledge/`)

Canonical, tool-neutral facts for IGNIS, in Open Knowledge Format (markdown + YAML frontmatter, one
concept per file, links are the graph edges). Start at `.agents/knowledge/index.md`.

It is also served over MCP by **`atlas`** (written into `.mcp.json` per machine by `vulcan sync`; it runs VULCAN's atlas with
`bun x --no-install vulcan x atlas mcp`; consumers outside this repo use `@venizia/vulcan-atlas`), the same server that answers over the wiki and the changelogs:

| Tool | Use it for |
|---|---|
| `search` | Find a chunk by keyword - pass `corpus: "knowledge"` to search this bundle only |
| `get` | Read one chunk in full, by the id a search hit returned |
| `symbol` | Locate an exported symbol: its package, import specifier, kind, signature and source line |
| `version` | Compare the `@venizia/*` packages installed in a directory with the newest known versions |
| `changes` | List the changelog entries between two versions of a package, or between two dates |

Maintaining it is rule P-03: change a fact in the code, update the concept in the same change.
Generated reference files come from `make okf-gen` (and `api-gen` for the API pages) - the okf target
is VULCAN's, included from `vulcan.mk`. `make okf-check-strict` validates (OKF v0.2 plus the house rules); it is a CI gate, not a
commit gate. The `docs-update` skill keeps the bundle in step with the code.

A skill is a procedure you follow; a concept is material you consult. Neither is duplicated in the

Code ships.

## Per-tool files (CLAUDE.md, GEMINI.md, ...)

This `AGENTS.md` is the single source. `make vulcan-sync` (`vulcan sync`) writes each tool's file as a
pointer to it (`CLAUDE.md` holds `@AGENTS.md`), never a copy, and writes `.claude/`: VULCAN's settings
and hooks (its session digest and the `guard-writes` check) and the shipped skills - `docs-update`
(it applies the D rules in `.agents/rules.md`), `docs-writing`. The
digest names the rules sessions drop most (`digest.oftenDropped` in `.configs/vulcan.config.mts`) and
prints the minimap shape from `.agents/rules.md`. Re-run `make vulcan-sync` after a pull that touched
`.configs/vulcan.config.mts` or the pinned VULCAN version; `make vulcan-doctor`
says when you need to.
